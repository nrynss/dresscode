# Feedback log

Friction and wins with the services and libraries Dresscode uses, recorded when they were hit. The submission's feedback, and issues for Keel, Chaaya and Lambo, are drafted from this file.

Each entry gives what happened, the evidence, what it cost, and what would fix it. Never paste a key.

## YouCam API

- **A stored key with a stray space is rejected as unrecognised.** The key read back from the keyring with one extra whitespace character got `401 InvalidApiKey` ("This API key is not recognized") from both the India and global servers; trimmed, it worked. *Fix:* trim keys when loading them, and say so in `docs/keys.md`.
- **v2 has no balance endpoint.** `/s2s/v2.0/client/credit` is `404`; the v1 path needs the older token flow. Units are visible only in the console. *Fix:* meter units ourselves through Keel `cost`, starting from the console balance T0.2 records.
  - **Correction (T0.5):** `GET /s2s/v1.0/client/credit` answers to the v2 API key as a plain Bearer token. It returned both pools (1,000 and 40) and matched the console. `GET /s2s/v1.0/client/credit/history` is a per-task ledger, and it wants `Content-Type: application/json` even on a GET (`415` without it). The unit-system page lists both, with the CLI's `youcam client credit`. *Fix:* Keel `cost` can settle against the real balance, not only a local meter.
- **A failed task is charged, then refunded into a different pool.** In the ledger, every engine error (no face, bad file, too small) shows `−1` from the 1,000-unit pool at create and `+1` "failed" a second later into the 40-unit trial pool. The net is 0, but units move to a pool with a different `expiry`. *Cost:* none. *Fix:* the meter must reserve at create and settle at the end; never read the balance mid-task as truth.
- **The units do expire.** docs/keys.md says they don't; the credit endpoint gives each pool an `expiry`. *Fix:* the user should check the console and correct docs/keys.md.
- **Makeup smooths skin unless told not to.** An omitted `skin_smooth` effect applies a default of 50. That is in the makeup page's schema, not its overview. The recorded lip without it shows pores gone and lighter skin. *Fix:* always send `skin_smooth` at 0. "Don't use `skin_smooth`" means "send it at zero".
- **Generative tasks redraw the face.** AI Smile and both hair-transfer templates smoothed the skin; the cloth task re-rendered the face with harsher texture; the hair updo removed the earrings. Only the composited jewellery and the lip left the face alone. *Cost:* those renders will likely fail the render check, so the hair and smile fixes may never be shown. *Fix:* the render check must compare skin texture, not only identity; the product may need to accept that some fixes stay a suggestion.
- **The necklace engine misplaces a flat product shot.** On a dim photo with hair over the neck, engine placement drew a long line over the hair. Explicit `necklace_anchor_point` (the chain's two ends in the product photo) and `necklace_wearing_location` (the two neck points) fixed it. *Cost:* one unit. *Fix:* the necklace fix needs neck points per photo; the product image's anchors can be fixed once per product.
- **Files and results sit in a US bucket.** Upload slots and result links are `yce-us.s3-accelerate.amazonaws.com` (`us-west-2`), although the API host is the India server. *Fix:* say so in the privacy text.
- **Content type and extension lie.** Makeup, earring and necklace results are PNG served as `binary/octet-stream` under a `.jpg` name. *Fix:* sniff the bytes.
- **Documented size limits are not the engine's.** Hair (≤ 1024), beard (< 1024) and makeup (height < 1080) all took 896 × 1200; beard returned 764 × 1024. Makeup's minimum is 320 × 320, not the documented 100 px. The File API validates nothing: a `text/plain` type, a declared 50 MB and a declared 0 bytes all get a slot. *Fix:* validate on our side before the slot; don't rely on the provider's errors for size.
- **No rate-limit headers.** No response carried one; the documented limit is 250 requests per 300 s per IP and per key. *Fix:* pace ourselves; treat `429` as the only signal.
- **Template titles don't match a dress code.** No hair template is titled "tied back", and no beard template is a short, even beard. The nearest are Casual Updo (a bun) and Circle (a goatee). *Fix:* the user decides which templates stand for `tied-back` and `short`, or the vocabulary changes.

## Cloudflare Workers AI

- **An account-owned token fails the user-token check.** A token made from the Workers AI template answers `Invalid API Token` at `/user/tokens/verify` but `active` at `/accounts/{id}/tokens/verify`, and works for inference. *Fix:* verify at the account path.

- **Clef is deterministic per request.** Ten repeats of one judge request (T0.6) returned the same answers to the last digit, and so did the first call. Probabilities come back with at most four decimals. *Cost:* none. *Fix:* nothing to fix; a retry for a second opinion buys nothing, and stability has to be measured across photos and image sizes instead.
- **A judge request with no image still answers.** The same seven family-function questions with the image left out came back yes at 0.65 to 0.86 on every criterion, not an error and not "can't tell". *Fix for the product:* the judge must refuse to call Clef without the photo, never trust such an answer.
- **Rewording one question moves the answers to the others.** Changing only `family-hair-finished`'s text (T0.6) shifted the other six family-function answers on the same photos: P12's expression went from 0.4616 to 0.612, P11's beard from 0.6431 to 0.5106, and V04's expression from 0.648 to 0.5943. Clef reads a request's questions together, not one at a time. *Cost:* every recording of that occasion had to be redone. *Fix:* treat the occasion's question set as one unit. A wording change re-records the whole occasion, and thresholds (T3.9) are measured on the final wording only.
- **The question text costs as much as the photo.** The judge's seven or eight questions are 942 to 1,079 input tokens; the 896 × 1200 photo is 1,002. The check's eleven vocabulary choices are about 2,090 tokens beside two photos at 1,002 each. `output_tokens` is always 0. The image count matches the documented tokenizer exactly (an image over 1 MP is scaled down; 768 × 1024 is 771 tokens, 576 × 768 is 435, 384 × 512 is 195). *Fix:* trimming question text saves as much as shrinking the photo.

## Lambo

- **Idle sessions expire in minutes.** Two orchestrator MCP sessions (`dc-u-orch-01`, `dc-u-orch-02`) died with `404 Session not found` after roughly 10–20 minutes of idling between calls; the next `tools/call` on the old `Mcp-Session-Id` was an HTTP `404` plain-text, not a JSON-RPC error. A later `initialize` with the same path works. *Cost:* two landing records were delayed, none lost — each was re-sent on a fresh session. *Fix for the product:* a real user's second visit can idle far longer than that, so Dresscode's memory client (T2.3) must treat `404 Session not found` as "initialize again, then replay the call", not as a failure. Worth checking whether T2.3's client already does; if not, that is a gap to close before T3.8.

- **Deliverability: the account-owner sender lands in spam.** The T2.4b confirmation send — from `onboarding@resend.dev` to the account owner's own Gmail — arrived in under a minute, in the spam folder. The sign-in code email expires in 10 minutes, so spam placement is not cosmetic: a judge digging a code out of spam is racing the clock. *Fix:* verify a sending domain (SPF/DKIM on the from-domain) before the demo and judging, and check placement again from the verified domain.

## Resend

- **Root cause of the nameless 403: the from-domain was not the verified one.** `RESEND_FROM` was `dresscode@nryn.dev`, but the verified domain in the Resend console is `send.nryn.dev` (verified, Resend Forge on, Cloudflare). The same one-send test from `dresscode@send.nryn.dev` was accepted in 401 ms — no console change needed, only the address. *Fix:* keep the from-address on a verified domain of the account; and treat an unnamed 403 as "look at the domain first".
- **A refused send carries no error name.** The T2.4b live send (one POST to `/emails`, 2026-10-30T13:38:42Z) answered `403` in 0.37 s with an empty `name`, where T2.4's recorded errors and Resend's docs carry a snake_case name such as `validation_error`. An unnamed 403 reads as account or domain gating (from-domain not verified, or the key lacking send permission), not message shape — but the response says none of that. *Cost:* one refused call, nothing; no mail, no retry. *Fix:* the console must say what the API will not; and the sender's typed `Refusal` should surface the name verbatim when Resend gives one, so an empty name is itself the tell.

## Svelte

- **A state variable named `state` breaks `svelte-check`.** T5.6's screen declared `let state = $state<HistoryState | undefined>(undefined)` and svelte-check answered "Block-scoped variable '$state' used before its declaration", "Untyped function calls may not accept type arguments", and "'state' implicitly has type 'any' … in its own initializer" — while `vitest` and `eslint` passed the same file clean. Renaming the variable to `switchState` cleared all of it with no other change. svelte2tsx's generated code has its own `state` binding, so a component variable of that name collides with it. *Cost:* most of a gate cycle, isolated by bisecting a probe copy. *Fix for the product:* never name a component's state variable `state`; nothing warns about it before `svelte-check` runs. Worth an issue on svelte-language-tools if it reproduces on a minimal file.

## Keel

- **The throttle clamps a Retry-After hint to `Max`.** `throttle.Config.Max` caps one wait however it was built, and a provider's hint is built like any other: `hintWait` clamps the hint to the ceiling before the spread, so a hint larger than `Max` is silently truncated and the call waits less than the provider asked, with no error saying so. A test (or caller) asserting the raw hint value must carry its own ceiling, or the clamp swallows it. Evidence: T2.2's rate-limit test initially asserted a 2 ms ceiling that a 1 s hint silently exceeded. *Cost:* one failing test and a read of the Keel source to find where the wait went. *Fix:* the rate-limit test now builds a client whose `Max` holds the one-second hint and bounds the wait from above as well as below; the clamp itself is documented, deliberate Keel behaviour.

## Go standard library

- **`image.DecodeConfig` does not stop at the JPEG frame header.** A minimal JPEG — SOI, one SOF0 segment, nothing else — comes back `unexpected EOF`: the config-only walk returns at SOF only when a JFIF APP0 marker has been seen, and otherwise keeps reading markers until a SOS or the input ends (image/jpeg's `decode`). T2.1's oversize test wanted a small byte payload that reads as a small picture, so the fixture appends a bare `FF DA 00 02` (SOS, length two) after the frame header; `DecodeConfig` then returns the dimensions. *Cost:* one failing test and an isolated reproduction. *Fix:* nothing to fix in the product; a header-only reader of someone else's JPEG needs either APP0 or SOS present.

## Vite

- **`<img>` loads bypass the mock's fetch interception.** The mock answers by overriding `globalThis.fetch`, and the T5.10 sample-JPEG mapping lives inside it — but an `<img src="/media/…">` is loaded by the browser's resource loader, which never calls the page's `fetch`. So in `pnpm dev` every picture on every screen still renders as a miss (alt text on the sunken fill) whatever the mock serves; a direct `curl /media/<id>` on the dev server returns `index.html`. The recorded bytes only reach responses the app reads through `fetch`. T5.13's browser pass hit it on the render comparator. *Fix for the product:* the real server serves the bytes, so it is dev-only; if dev screenshots ever need the photographs, the mock needs a Vite middleware or blob-URL mapping, not more fetch wiring.
