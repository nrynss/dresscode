# Feedback log

Friction and wins with the services and libraries Dresscode uses, recorded when they were hit. The submission's feedback, and issues for Keel, Chaaya and Lambo, are drafted from this file.

Each entry gives what happened, the evidence, what it cost, and what would fix it. Never paste a key.

## YouCam API

- **A stored key with a stray space is rejected as unrecognised.** The key read back from the keyring with one extra whitespace character got `401 InvalidApiKey` ("This API key is not recognized") from both the India and global servers; trimmed, it worked. *Fix:* trim keys when loading them, and say so in `docs/keys.md`.
- **v2 has no balance endpoint.** `/s2s/v2.0/client/credit` is `404`; the v1 path needs the older token flow. Units are visible only in the console. *Fix:* meter units ourselves through Keel `cost`, starting from the console balance T0.2 records.
  - **Correction (T0.5):** `GET /s2s/v1.0/client/credit` answers to the v2 API key as a plain Bearer token. It returned both pools (1,000 and 40) and matched the console. `GET /s2s/v1.0/client/credit/history` is a per-task ledger, and it wants `Content-Type: application/json` even on a GET (`415` without it). The unit-system page lists both, with the CLI's `youcam client credit`. *Fix:* Keel `cost` can settle against the real balance, not only a local meter.
- **A failed task is charged, then refunded into a different pool.** In the ledger, every engine error (no face, bad file, too small) shows `−1` from the 1,000-unit pool at create and `+1` "failed" a second later into the 40-unit trial pool. The net is 0, but units move to a pool with a different `expiry`. *Cost:* none. *Fix:* the meter must reserve at create and settle at the end; never read the balance mid-task as truth.
- **The units do expire.** docs/keys.md says they don't; the credit endpoint gives each pool an `expiry`. *Fix:* the user should check the console and correct docs/keys.md.
- **Makeup smooths skin unless told not to.** An omitted `skin_smooth` effect applies a default of 50. That is in the makeup page's schema, not its overview. The recorded lip without it shows pores gone and lighter skin. *Fix:* always send `skin_smooth` at 0. "Don't use `skin_smooth`" means "send it at zero".
- **Generative tasks redraw the face.** AI Smile and both hair-transfer templates smoothed the skin; the cloth task re-rendered the face with harsher texture; the hair updo removed the earrings. Only the composited jewellery and the lip left the face alone. *Cost:* those renders will likely fail the render check, so the hair and smile fixes may never be shown. *Fix:* the render check must compare skin texture, not only identity; the product may need to accept that some fixes stay a suggestion.
- **The necklace engine misplaces a flat product shot.** On a dim photo with hair over the neck, engine placement drew a long line over the hair. Explicit `necklace_anchor_point` (the chain's two ends in the product photo) and `necklace_wearing_location` (the two neck points) fixed it. *Cost:* one unit. *Fix:* the necklace fix needs neck points per photo; the product image's anchors can be fixed once per product.
- **Files and results sit in a US bucket.** Upload slots and result links are `yce-us.s3-accelerate.amazonaws.com` (`us-west-2`), although the API host is the India server. *Fix:* say so in the privacy text.
- **Content type and extension lie.** Makeup, earring and necklace results are PNG served as `binary/octet-stream` under a `.jpg` name. *Fix:* sniff the bytes.
- **Documented size limits are not the engine's.** Hair (≤ 1024), beard (< 1024) and makeup (height < 1080) all took 896 × 1200; beard returned 764 × 1024. Makeup's minimum is 320 × 320, not the documented 100 px. The File API validates nothing: a `text/plain` type, a declared 50 MB and a declared 0 bytes all get a slot. *Fix:* validate on our side before the slot; don't rely on the provider's errors for size.
- **No rate-limit headers.** No response carried one; the documented limit is 250 requests per 300 s per IP and per key. *Fix:* pace ourselves; treat `429` as the only signal.
- **Template titles don't match a dress code.** No hair template is titled "tied back", and no beard template is a short, even beard. The nearest are Casual Updo (a bun) and Circle (a goatee). *Fix:* the user decides which templates stand for `tied-back` and `short`, or the vocabulary changes.
- **An analysis recording names no face.** `face-attr-upload-src` says the picture it uploaded and `http-face-attr-poll` says the shape it answered, but nothing in the pair says whose look a later story may treat as cached. T4.6 found a sample cache carrying `Oval` for V14 from the only recorded read, which was of V06: right value, wrong person, and the file read as if YouCam had measured this selfie. *Fix:* a cached provider reading carries the picture it read, and the loader refuses it unless that picture is the same person's; the recording pair stays silent about both, so the check belongs to whoever writes the cache, not to the client.

## Cloudflare Workers AI

- **An account-owned token fails the user-token check.** A token made from the Workers AI template answers `Invalid API Token` at `/user/tokens/verify` but `active` at `/accounts/{id}/tokens/verify`, and works for inference. *Fix:* verify at the account path.

- **Clef is deterministic per request.** Ten repeats of one judge request (T0.6) returned the same answers to the last digit, and so did the first call. Probabilities come back with at most four decimals. *Cost:* none. *Fix:* nothing to fix; a retry for a second opinion buys nothing, and stability has to be measured across photos and image sizes instead.
- **A judge request with no image still answers.** The same seven family-function questions with the image left out came back yes at 0.65 to 0.86 on every criterion, not an error and not "can't tell". *Fix for the product:* the judge must refuse to call Clef without the photo, never trust such an answer.
- **Rewording one question moves the answers to the others.** Changing only `family-hair-finished`'s text (T0.6) shifted the other six family-function answers on the same photos: P12's expression went from 0.4616 to 0.612, P11's beard from 0.6431 to 0.5106, and V04's expression from 0.648 to 0.5943. Clef reads a request's questions together, not one at a time. *Cost:* every recording of that occasion had to be redone. *Fix:* treat the occasion's question set as one unit. A wording change re-records the whole occasion, and thresholds (T3.9) are measured on the final wording only.
- **The question text costs as much as the photo.** The judge's seven or eight questions are 942 to 1,079 input tokens; the 896 × 1200 photo is 1,002. The check's eleven vocabulary choices are about 2,090 tokens beside two photos at 1,002 each. `output_tokens` is always 0. The image count matches the documented tokenizer exactly (an image over 1 MP is scaled down; 768 × 1024 is 771 tokens, 576 × 768 is 435, 384 × 512 is 195). *Fix:* trimming question text saves as much as shrinking the photo.

## Lambo

Worth checking whether T2.3's client already does; if not, that is a gap to close before T3.8.

The sign-in code email expires in 10 minutes, so spam placement is not cosmetic: a judge digging a code out of spam is racing the clock. *Fix:* verify a sending domain (SPF/DKIM on the from-domain) before the demo and judging, and check placement again from the verified domain.

## Resend

- **Root cause of the nameless 403: the from-domain was not the verified one.** `RESEND_FROM` was `dresscode@nryn.dev`, but the verified domain in the Resend console is `send.nryn.dev` (verified, Resend Forge on, Cloudflare). The same one-send test from `dresscode@send.nryn.dev` was accepted in 401 ms — no console change needed, only the address. *Fix:* keep the from-address on a verified domain of the account; and treat an unnamed 403 as "look at the domain first".
- **A refused send carries no error name.** The T2.4b live send (one POST to `/emails`, 2026-10-30T13:38:42Z) answered `403` in 0.37 s with an empty `name`, where T2.4's recorded errors and Resend's docs carry a snake_case name such as `validation_error`. An unnamed 403 reads as account or domain gating (from-domain not verified, or the key lacking send permission), not message shape — but the response says none of that. *Cost:* one refused call, nothing; no mail, no retry. *Fix:* the console must say what the API will not; and the sender's typed `Refusal` should surface the name verbatim when Resend gives one, so an empty name is itself the tell.

## Svelte

- **A state variable named `state` breaks `svelte-check`.** T5.6's screen declared `let state = $state<HistoryState | undefined>(undefined)` and svelte-check answered "Block-scoped variable '$state' used before its declaration", "Untyped function calls may not accept type arguments", and "'state' implicitly has type 'any' … in its own initializer" — while `vitest` and `eslint` passed the same file clean. Renaming the variable to `switchState` cleared all of it with no other change. svelte2tsx's generated code has its own `state` binding, so a component variable of that name collides with it. *Cost:* most of a gate cycle, isolated by bisecting a probe copy. *Fix for the product:* never name a component's state variable `state`; nothing warns about it before `svelte-check` runs. Worth an issue on svelte-language-tools if it reproduces on a minimal file.
- **A component's scoped style outranks a global recipe of the same selector.** T5.20's `.disclosure` recipe in `theme.css` sets `display: flex` on `.disclosure > summary`, but `account.svelte`'s own `<style>` says `.disclosure summary { display: inline-flex }` — and the compiled scoped rule carries the component's `svelte-…` attribute, so it wins the cascade and the recipe's display never applies. The recipe only ever lands where the screen stays silent. *Cost:* one browser pass before the accordion looked like a card rather than an inline label. *Fix for the product:* write a global recipe per property and let each screen's own paddings ride on top; where the screen's rule cannot be overridden, choose a property it never names — `align-self: stretch` on both the card and its summary is what actually gets a full-width row out of an `inline-flex` summary, because no screen sets it. The recipes `verdict.svelte`, `render.svelte` and `history.svelte` already set `display: flex` with their own `::after "▾"`, so they match the global shape and need no change.

## Keel

- **Two runners over one `jobs` table strand each other's work on restart.** `job.Open` recovers every unfinished row its store shows: it marks each `interrupted`, publishes that terminal on its own broker, and resumes only the kinds it was given. Two mounts sharing one database (looks and deletion) each call `job.Open`, so whichever opens first interrupts the other's in-flight jobs and cannot resume them — an account deletion left `interrupted` with no replacement, and its terminal published on a broker its own subscribers do not hold. `jobsql.Config.Namespace` names only the migration ledger, not the table, so the stores cannot be separated, and a `Runner` has no way to add a kind after `Open`. *Cost:* found by review before any process mounted both; a restart would have stranded a half-done erase. *Fix in Dresscode:* a `job.Store` wrapper that filters `Unfinished` to the runner's own kinds (`internal/server/jobs.go`). *Fix for Keel:* either scope recovery to the configured kinds, or let a caller register kinds on an open runner so one process can share one runner.
- **A stream subscriber with no cursor gets the retained terminal alone.** `ServeTopic` registers the subscription before it writes the header, and `catchUp` replays the ring only after a resume cursor; with no cursor and a retained terminal on the topic, that terminal is the only frame a late subscriber receives. `Last-Event-ID: 0` is not a cursor either — `lastEventID` reads empty, unparseable and `0` alike as "no cursor". The handler also stays up after the terminal frame, so a client reading to EOF waits out its own deadline. *Cost:* every stream test in T4.4 took the full 30 s deadline and saw one frame, until the rig parked the first model ask, subscribed live, released on the headers and stopped reading at the terminal. *Fix for the product:* the phone reconnects with the last id it read, and a test that wants the whole stream must be subscribed before the job runs. *Fix for Keel:* document the no-cursor case beside `ServeTopic`, and treat a `0` cursor as "from the start" or say why it is not one.

- **The throttle clamps a Retry-After hint to `Max`.** `throttle.Config.Max` caps one wait however it was built, and a provider's hint is built like any other: `hintWait` clamps the hint to the ceiling before the spread, so a hint larger than `Max` is silently truncated and the call waits less than the provider asked, with no error saying so. A test (or caller) asserting the raw hint value must carry its own ceiling, or the clamp swallows it. Evidence: T2.2's rate-limit test initially asserted a 2 ms ceiling that a 1 s hint silently exceeded. *Cost:* one failing test and a read of the Keel source to find where the wait went. *Fix:* the rate-limit test now builds a client whose `Max` holds the one-second hint and bounds the wait from above as well as below; the clamp itself is documented, deliberate Keel behaviour.

- **`cost/sqlitestore.Open` rewrites the ceiling on every open, including a zero.** `setLimit` runs unconditionally at open with `Config.Limit`, an upsert on the budget row: open with `Limit` unset (the zero value) and a store that held a live ceiling now reads zero, and a running server sharing the file refuses every reservation until something reopens with the real number. Deliberate — "a redeploy can raise or lower the ceiling" — but it makes "read the books" a write. T4.7's budget command must therefore load the settings file and open with its numbers, not open empty and read the stored ceiling back; there is also no getter for one owner's ceiling, so a report derives per-owner ceilings from the settings, not the store. *Cost:* one design dead-end caught before it shipped; the first sketch opened the store twice (open, read limit, reopen) before noticing the first open had already rewritten it. *Fix for the product:* never open a spend namespace without its real `Limit`. *Fix for Keel:* a read-only open, or an `Open` that leaves an existing ceiling alone when `Limit` is omitted.

- **`config`'s strict parser cannot load a slice of the file.** Unknown keys are fatal, so decoding into a struct that omits `[secrets.*]` fails on the sections it does not name; a load that wants only `[budgets]` must still resolve every required key, keyring lookups included. T4.7's `dresscode budget` therefore resolves all ten key references (through the same `config.Load` the server runs) to print two ceilings — it prints none of the values, but it reads them all. *Cost:* one abandoned partial-decode sketch. *Fix for the product:* none; the operator runs the command where the keys live. *Fix for Keel:* a documented way to load a subset, or an explicit statement that the file is all-or-nothing.

- **`Runner.Result` reads; it does not wait.** Its own comment lists the three states, and the shape follows from the store: one `Get` and the current status, so `StatusRunning` comes back as easily as a terminal. A handler that starts a job and wants to answer only once the job has settled therefore has nothing to call — the choices are polling the store or subscribing to `Topic(id)`, which is the client's job, not the server's. *Cost:* found while deciding whether T4.6's sample open could honour docs/api.md's "the job is already `done`"; awaiting would either spin on the store or put a free route's latency behind the paid queue's concurrency gate (the zero `Kind` runs `defaultLimit` = 16 at once). *Fix for the product:* this is why T4.6 lands the sample job terminal at open instead of running it on the runner and reading it back — see the next entry; `Result` still reads without waiting, and the app's single read is served by the row already being done. *Fix for Keel:* either say in `Result`'s comment that it never blocks, or give the caller a wait that is bounded by the caller's context.

- **A terminal job row can be written straight into the store, from outside a runner.** `jobsql.Open` is a handle on the `jobs` table, not a lease on a runner: `Create` with a full `job.Record` (`Status` done, `Attempt` 1, `RootID` = its own `ID`, `Data` the finished result, `Progress` the last stage) inserts a row the landed reads cannot tell from one a runner finished. `Runner` reaches a job only through `Get` by id or root and the attempt walk, both of which just read what is there, so the look routes, `job/done` state and the `Topic(id)` stream all answer a row that was never run — and `job.Open`'s recovery lists `Unfinished`, which a terminal-at-birth row never enters, so it survives a restart untouched and is never offered to a resume hook. `Progress` and `Data` must be shaped exactly as the runner would leave them (T4.6's `land` sets `Progress` to the last buffered frame and `Data` to the finished look), because a reader that decodes them has no way to know the row skipped the pipeline. *Cost:* none — found while designing T4.6's born-finished open, and it is what let that route take no lease, no gate and no runner slot. *Fix for Keel:* nothing is broken, but the store's write-without-a-runner is load-bearing and undocumented; a note beside `jobsql.Open`/`job.Record` saying a caller may seed a finished record (and which fields the readers then trust) would save the next person rediscovering it.
- **`mediastore.Store` has no way to ask what it holds.** `Open` gives a `*Store` whose methods are all keyed by blob id — `Persist`, `PersistWithID`, `Open`, `TempCopy`, `Delete`, `DeleteIfPresent`, `Adopt`, `Snapshot`, `ServeHTTP` — and the listing that answers "which blobs does this owner hold" (`Blobs(ctx)`) is a method of the `BlobIndex` behind it, not of the Store, so an app that reached the store through a mount which kept only the `*Store` cannot enumerate: T4.6's `privacy.Blobs` interface is satisfied in tests by a fake and in production by the composition hand passing the index handle it opened. Worse for a content lookup, `sqlitestore`'s `media` rows carry `id, owner, media_group, content_type, size_bytes, visibility, created_at` and **no digest** — `Adopt` hashes bytes to *verify* a client's upload, but nothing stores or indexes the hash, and `Snapshot`'s `Selection` takes only `IDs` and `Owner`. So "reuse the blob I already hold for these bytes" has no supported answer at all. *Cost:* the first sketch of T4.6's dedup called `env.media.Blobs(ctx)` and failed to compile. *Fix for the product:* `samples.go`'s `held` reads the index's own table on the shared SQLite file for a shortlist (`owner`, `media_group`, `size_bytes`, newest first, capped at `keepSearch`) and then hashes the bytes back through the store's own `Open`, which is the only path that gives an identity. *Fix for Keel:* a digest column plus a `Store.Lookup(ctx, owner, group, sha256)` — or at least `Store.Blobs(ctx)` promoted from the index — would let a caller dedup without hand-writing SQL against a dependency's schema.

## Go standard library

- **`image.DecodeConfig` does not stop at the JPEG frame header.** A minimal JPEG — SOI, one SOF0 segment, nothing else — comes back `unexpected EOF`: the config-only walk returns at SOF only when a JFIF APP0 marker has been seen, and otherwise keeps reading markers until a SOS or the input ends (image/jpeg's `decode`). T2.1's oversize test wanted a small byte payload that reads as a small picture, so the fixture appends a bare `FF DA 00 02` (SOS, length two) after the frame header; `DecodeConfig` then returns the dimensions. *Cost:* one failing test and an isolated reproduction. *Fix:* nothing to fix in the product; a header-only reader of someone else's JPEG needs either APP0 or SOS present.

- **`filepath.EvalSymlinks` fails over the missing directory, not the missing file.** A story naming `../youcam/results/<name>.jpg` mounted against a samples directory with no `../youcam` sibling is refused by `EvalSymlinks` with `lstat <base>/youcam: no such file or directory` - it never reaches `os.ReadFile`, whose own error would have said `open <base>/youcam/results/<name>.jpg`. T4.6's F5 wanted the mount fault to name the two roots a story reads from, and wrapping only the read would have missed the commonest layout mistake entirely. *Fix:* `samples.go`'s `missingSamplePicture` wraps **both** the resolve and the read, and `TestASampleMountNamesTheRootsWhenAPictureIsMissing` mounts a directory that holds the five stories and the people and no sibling at all.

## Vite

- **`<img>` loads bypass the mock's fetch interception.** The mock answers by overriding `globalThis.fetch`, and the T5.10 sample-JPEG mapping lives inside it — but an `<img src="/media/…">` is loaded by the browser's resource loader, which never calls the page's `fetch`. So in `pnpm dev` every picture on every screen still renders as a miss (alt text on the sunken fill) whatever the mock serves; a direct `curl /media/<id>` on the dev server returns `index.html`. The recorded bytes only reach responses the app reads through `fetch`. T5.13's browser pass hit it on the render comparator. *Fix for the product:* the real server serves the bytes, so it is dev-only; if dev screenshots ever need the photographs, the mock needs a Vite middleware or blob-URL mapping, not more fetch wiring.

## Playwright

- **Styled controls refuse the programmatic click on their hidden input.** Dresscode's own chips, switches and now fix pills hide the real `<input>` (1 px, `opacity: 0`) behind styled chrome, and Playwright refuses both `.check()` and a raw input click with "covered by … tick span" — the chrome is exactly what a real pointer would hit. The label click is the path a finger takes and works in a real browser; in jsdom (the mounted gates) it is the input's own click that must be used, and jsdom fires the change event fine. Third hit across T5.12, T5.14 and T5.15. *Fix for the product:* none — the controls are honest; the rule for tests is label click in browsers, input click in jsdom.
- **A classic scrollbar shrinks the layout viewport.** At a fixed 375 px window a desktop Chromium with classic scrollbars reports `clientWidth` 360 (15 px of scrollbar) once the page grows taller than the viewport, so a header that fits one line at true 375 wraps the moment a drawer above the fold opens the page. Phones use overlay scrollbars and keep the full 343 px of shell content. *Fix for the product:* judge phone layout by the true 375 (or expect the wrap in desktop screenshot passes); `scrollbar-gutter` would trade the no-scrollbar case to fix this one, not worth it.
- **A screenshot pass needs no Playwright driver.** `~/.cache/ms-playwright` carried Chromium builds but no playwright package was installed anywhere, so T5.18's closing set ran on `google-chrome-stable --headless=new --remote-debugging-port` driven by raw CDP over Node's built-in WebSocket (`Emulation.setDeviceMetricsOverride` for the 375/768 viewports, `Page.captureScreenshot` with `captureBeyondViewport` for full-page shots, `Runtime.evaluate` for the drawer and dialog walks). Device emulation with `mobile: true` keeps overlay scrollbars, so the 375 shots measure the true width; forcing the theme needs a warm boot on the origin, a `localStorage["chaaya-theme"]` write, then a reload, because Chaaya reads the theme at startup. *Cost:* none. *Fix for the product:* none needed; the recipe is in `/tmp/t518-shots/shoot.mjs` while the pass lasts.
- **A closed `<details>` hides its whole subtree from the accessibility gate.** axe-core 4.14's `detailsHidden` pruning (`axe.js:19132-19146`) drops every child of a `details` that lacks the `open` attribute, so markup folded behind a disclosure stops being scanned at all. Reproduced on this repo's own jsdom 30.1.3 + axe 4.14.0: an unlabelled `<input>` appended inside a closed drawer gives `a11yGate` **zero** violations, and the same node once the drawer is open gives `axe critical: label on 1 node(s)`. T5.18 collapsed three disclosures and added a mounted open state for only one of them, so two screens' content went unjudged with every test green — the trap any declutter pass that folds markup away can fall into, and the reason `SSR still renders the children` does not save a mounted gate. *Fix for the product:* every disclosure a screen gains gets an open state in `screens.test.ts` beside its closed one, and the pruning is cheap to prove: inject a known violation into the drawer's content and watch the gate answer only when it is open.
- **A fixed bottom bar is invisible to the mounted gate.** jsdom returns zero-size boxes for everything, so `a11yGate` and the contrast sweep cannot see content sitting under `position: fixed` chrome, and `scrollWidth <= 375` in jsdom is a tautology — it holds whether the page overflows or not. T5.20's tab bar therefore rests on two proofs the gate cannot fake: a static guard that reads `shell.svelte`'s CSS text for the pieces that keep the bar inside a phone column (`repeat(4, minmax(0, 1fr))`, no width on the bar, the `env(safe-area-inset-*)` padding, the label's `overflow-wrap`) plus `theme.css`'s grown last measure, and a real-browser pass measuring `documentElement.scrollWidth`, the tab grid's rect and the last content element's bottom edge against the bar's top edge, in both themes at 375, 768 and 1280 px. *Cost:* none, but only because the browser pass was run; a green gate alone would have proved nothing about the bar. *Fix for the product:* when a change is layout, gate it on text the tests can read and measure the geometry in a browser, and say so in the notes when a clause has no automated proof.
- **A `1fr` grid track is a minimum-content track, so one long tab label can widen the bar past the viewport.** With `grid-template-columns: repeat(4, 1fr)` at 375 px, a label that cannot break (a 40-character word) sets each column's floor at its own min-content width and the grid spills sideways — `1fr` is `minmax(auto, 1fr)`, and `auto` is the trap. `repeat(4, minmax(0, 1fr))` with `overflow-wrap: anywhere` on the label span holds at 375 px. *Cost:* caught by measuring, not by the gate. *Fix for the product:* the recipe is pinned in `shell-nav.test.ts`'s static guard.

## Chrome

- **A closed `<details>` still lays its children out — and getBoundingClientRect reports those boxes.** Chrome 156 skips painting a closed drawer's body (content-visibility style hiding), but the elements keep real layout boxes, so a "nothing sits under the fixed bar" walk that takes the max `bottom` over elements with `height > 0` reads thousands of pixels from drawers nobody opened. T5.20's browser guard hit it on the account screen: the two closed drawers reported bottoms past 5900 px on a 996 px document. *Fix for the test:* measure only what a reader can see — `el.checkVisibility({ checkVisibilityCSS: true, checkContentVisibility: true })` before trusting its rect. *Fix for the product:* none; the drawers are honest.
- **A CDP-driven test file must declare the Node environment, or it silently gets jsdom's WebSocket.** The a11y vitest config sets `environment: "jsdom"`, and jsdom's `WebSocket` global shadows Node 26's built-in — it refused the `ws://127.0.0.1` DevTools socket with a bare error and no network attempt. One line fixes it: `// @vitest-environment node` at the top of the file that drives Chrome (it needs no DOM anyway; the page is measured in the browser). *Fix for the product:* none.
- **`Page.loadEventFired` fires before a mounted app's modules do, and one `Runtime.evaluate` can bind to a mid-swap execution context.** The first shell probe after a navigation answered `null` (or ran against the previous document) while the same page answered normally milliseconds later, and a scroll issued in that window silently clamped to the unmounted page's height. The working recipe in `browser-shell.test.ts`: re-dispatch the probe fresh every 50 ms until the app's root is present (a new evaluate binds to whatever context is current), scroll repeatedly until `scrollHeight` is stable across frames (a screen fills its data a tick after the shell mounts), then measure. *Cost:* three probe runs. *Fix for the product:* none; the rig is in the repo now, not `/tmp`.
- **jsdom performs no layout, so `scrollWidth <= 375` cannot see a `position: fixed` bar — it is a tautology there.** `web/tests/a11y/` mounts through the vitest config that sets `environment: "jsdom"`, where a fixed element gets zero boxes. T5.20's review proved it on its own guard: `.tab-bar { margin-inline: -1rem }` pushes the bar to `-16..391` and its tabs to `-8..383` at a 375 px viewport while `scrollWidth`, `body.scrollWidth` and `clientWidth` all still report exactly **375** and all 67 a11y tests stay green. Two consequences for a mobile-layout claim: a CSS-**text** pin (`readFileSync` + regex) proves only which strings are in the file, so a semantically-equivalent-looking deletion passes it — deleting `.disclosure > summary { align-self: stretch }` collapsed real summaries from 341 px to 196 with the whole gate green — and the only honest guard is a browser-side per-element rect assertion, which needs no new dependency here (`google-chrome-stable` + Node 26's built-in WebSocket over the CDP recipe recorded two entries above; 14 route×theme measurements in ~90 s). A second jsdom trap surfaced in the same round: `min-width: 40rem` looked applied in the CSSOM yet computed `minWidth: "0px"`, because the same block ends `min-inline-size: 0` and the logical property wins. *Cost:* the T5.20 brief asserted this suite was Chromium-backed, and the guard shipped believing it covered a fixed bar. *Fix for the product:* geometry claims get a browser-backed assertion; a jsdom test may assert reachability, roles and axe semantics, never a rect.
